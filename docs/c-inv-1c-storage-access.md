# C-INV-1C 库位与 CTU 停靠点契约

## 颜色不是通行语义

`docs/topologies/666.json` 是拓扑事实来源，前端颜色只负责显示。当前 3D 配色中，
`road` 使用深蓝色，`conveyor` 使用蓝色，CTU 库区/货架使用青色，四向车库区使用橙色，
`blocked` 使用红色。任何颜色都不能被反向解析成道路、库位或取货权限。

车辆通行判断必须读取 Cell 的真实 `type`、楼层、库区归属和路网连通性。
Storage Node 表示商品所在的物理库位，不是车辆可行驶 Cell，也不能作为 A* / Dijkstra 的终点。

## 666 现状审计

对当前 666 拓扑执行确定性审计得到：

- Storage Node：2496 个，均属于 CTU 库区；
- 可直接验证的正式停靠点：0 个；
- 具备必要结构但仍需人工审核的候选：0 个；
- 当前不可映射库位：2496 个；
- 主要原因：2495 个库位没有符合取货面的相邻真实 CTU road；
- 另有 1 个库位附近的 road 同时存在取货面不符、与 Storage Node 几何占位重叠、道路孤立问题。

666 中虽然存在 road Cell，但绝大多数属于四向车库区。唯一带 CTU 库区标签的 road
`cell-r37-c85` 是孤立点并与库位几何占位冲突。另有少量未标注库区的 road，缺少 CTU
通道归属与取货面语义，不能据此批准正式映射。

因此，C-INV-1C 不会为了消除警告自动创建任何映射，也不会将“最近道路”认定为合法停靠点。

## 候选与正式映射

候选只能来自拓扑中真实存在的 `road` Cell。后端依次校验：

1. Storage Node 与 Cell 均存在且在同一楼层；
2. Cell 类型确实为 `road`，不允许 storage、blocked、buffer 或 conveyor；
3. 道路属于 CTU 库区；
4. 道路位置未被 Storage Node 占用；
5. 道路位于可从库区几何推导出的货架取货面；
6. 道路接入至少包含两个节点的 CTU road 连通分量；
7. 不能隔着其他货架、障碍物或输送带取货。

候选状态如下：

- `eligible`：结构语义完整，仍需用户显式勾选审核确认后才能保存；
- `review_required`：真实道路及基本结构有效，但拓扑缺少足够的货架朝向语义；只能由人工核对后以 `manual_verified` 来源保存；
- `rejected`：违反硬性安全规则，不能保存。

正式映射保存在数据库 `storage_access_mappings`，不会写回 666 JSON，也不会修改库存数量或预留数量。
拓扑版本变化后，旧映射必须重新校验；失效映射返回 `invalid` 或
`topology_version_mismatch`，不能继续用于路径规划。

## 路径规划边界

取货路径预览采用：

`CTU 当前 road Cell -> 真实 CTU road 路网 -> 已审核 access_cell_id`

规划复用现有 A* / Dijkstra，但输入图只包含通过校验的 CTU road Cell。返回结果标记为
`planning_preview_only`。到达停靠点不等于完成 Pick，本 Gate 不扣减、不预留、不释放库存。

未配置映射、映射版本不一致、映射失效或起点不在合法 CTU road 路网上时，规划必须失败并返回明确原因。

## 后续拓扑补充要求

在 C-INV-2 将取货任务接入正式流程之前，需要由仓库建模负责人补充并确认：

- CTU 蓝色通道对应的真实 road Cell 及 CTU 库区归属；
- 每排货架的朝向和允许取货面；
- 通道与货架之间可供 CTU 停靠和操作的空间；
- 道路连接、障碍物和输送带边界；
- 拓扑版本更新策略。

在上述信息进入可版本化拓扑契约之前，666 的 2496 个库位继续保持 `unconfigured`。
