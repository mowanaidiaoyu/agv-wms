# 修改清单：地面输送线（四向车整箱出货）

- 日期：2026-10-27
- 主题：区分两类输送线——架空输送线（零散件，CTU 交付，现状保留）与新增的地面输送线（整箱，四向车从车库出货用，贴地无支腿）；port 按所靠输送线类型分流派单，消除四向车库一层与相邻输送线的高度差。

---

## 背景

用户反馈：四向车将货物从四向车库搬送到输送线时，车库第一层与紧挨着的输送线存在高度差。实际业务有两类输送线：搬运零散件的是现有架空线（带面 1.66、有支腿、可双层 + 升降移栽机）；搬运四向车库出来的整箱货的输送线在地上（贴地单层）。需要补齐地面输送线并让四向车走它出货。

高度差实测：架空线带面 = `CONVEYOR_DECK_BASE(1.5) + 0.16`；四向车 L1 轨道面 = 0.35（`SHUTTLE_LEVEL_HEIGHT/4`）。地面线带面取 0.18，与四向车 L1 衔接。

## 设计

- 不新增 cell 类型，在 conveyor 格上加可选标记 `conveyorGround`（布尔，缺省 false=架空）。所有既有输送线逻辑（2×2 块、方向、寻路占用、滚筒合批）对两类线通用，只有高度/渲染/派单分流读取该标记。
- port 归属：入口格曼哈顿 ≤5 格内最近的输送块是地面块 → 该 port 为地面线 port；否则架空线 port（附近无输送块也按架空，兼容旧拓扑）。
- 派单分流：CTU 任务（零散件）只派架空线 port；四向车任务（整箱）只派地面线 port；只画了一种线时回退全部 port（保持旧行为）。
- 四向车交付后即完成任务（`_pick_station_for` 原本就只对 CTU 返回拣货位），货箱沿地面带面走到输送线末端淡出，不进人工拣货链路。

## 追加（同日第三轮：合同读取仍慢的最终优化）

用户反馈 Demo 6.6 读取 ShuttleGraph 仍然很慢。实测（后端带 --reload 已加载前两轮修复）：冷 853ms / 热 377ms。分解热路径：repo 读库+解析 897KB 拓扑 ~75ms、revision 哈希（json.dumps+sha256）~52ms、**FastAPI 对 1402 个轨道节点的 jsonable_encoder 逐字段编码 ~230ms（隐藏大头）**。

### 修复（`backend/app/api/routes.py`）

- 合同响应按 `(topology_id, topologyRevision, configRevision)` 缓存序列化后的 JSON 字节（有界 16 条），路由直接返回 `Response(content=bytes, media_type="application/json")`，跳过逐字段编码与重复 dumps；拓扑编辑或配置变更（revision 变）自动失效。

### 实测（用户运行中的 8000 实例，--reload 自动生效）

| 阶段 | 最初 | 第二轮后 | 本轮后 |
| --- | --- | --- | --- |
| 热路径（缓存命中） | ~5400 ms | ~377 ms | **~144–175 ms** |
| 冷路径（重启后首次） | ~5400 ms | ~853 ms | ~450 ms–2.2 s（含解释器预热，一次性） |

剩余热路径成本 = 读库解析 ~75ms + revision 哈希 ~52ms + 缓存命中返回；如需再快可缓存解析后的拓扑载荷，当前已无明显感知。

## 追加（同日第四轮：仿真 tick 循环 CPU 失控——"10 多分钟搞不完"的真凶）

用户反馈"读取还是很慢，10 多分钟都搞不完"。排查发现慢的不是合同接口，而是**仿真 tick 循环把后端事件循环占死**（worker 烧掉 380s CPU），所有请求排队。用户 10:59 启动的运行 `run-6030f1f1` 实际跑了 8.5 分钟才完成 2 个任务。

### 根因

- 分配器每 tick 对每对「空闲机器人 × 待处理任务」调用 `task_cost` → `shortest_path_shuttle` / `shortest_path`；
- 而 `build_shuttle_lookup`（全车库槽位×4 层掩码，~14ms）与 `build_walkable_lookup`（全网格 216×129=27,864 格）**每次调用都从全量拓扑重建**；
- 未能分配的任务保持 pending → 每 tick 重试：350 tick × ~20 次规划 × 重建成本 ≈ 300–500ms/tick → tick 循环跑不满实时，350 tick 实测 8.5 分钟，CPU 打满。

### 修复（`backend/app/services/pathfinding.py`）

- 新增按 `id(topology)` 的派生结构缓存 `_derived_cache`（持有拓扑强引用防 id 复用，上限 4 份；拓扑编辑/新运行解析出新 dict → 新 id → 自动失效）：
  - `build_shuttle_lookup` / `build_walkable_lookup` / `build_occupied_lookup` 结果缓存（occupied 返回副本防调用方修改）；
  - `shortest_path_shuttle` 路径按 `(起点, 终点, 层, 策略)` 记忆化（不可达结果同样缓存，返回副本防修改，上限 4096 条）——机器人待命时每 tick 的重复规划降为 O(1)。
- 已审计无调用方原地修改拓扑 dict；`shortest_path(avoid_storage)` 的过滤走字典推导生成新 dict，不污染缓存。

### 实测

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| shuttle 查找构建 | 14.2 ms/次 | 0.001 ms（缓存命中） |
| 单次路径规划（重复起终点） | ~4–100 ms（不可达更贵） | ~0.002 ms |
| 每 tick 分配开销 | ~300–500 ms | 毫秒级 |
| 350 tick 运行实测 | 8.5 分钟、CPU 打满 | 正常实时节奏 |

- 后端 `pytest -q`：**71 passed**。

## 追加（同日第五轮：py-spy 实测——tick 循环仍有三处热点 + 配置戳再次失配）

用户反馈"还是不行"。py-spy 对激活运行采样（10s 折叠栈）定位到三处剩余热点，合计占 CPU ~60%+：

1. **`shortest_path(avoid_storage=True)`**（CTU 分配检查，每 tick 每对调用）：每次从缓存的 27,864 格基表再全量过滤重建 + `storage_entry_dirs(topology)` 全拓扑重扫。→ 修复：`_walkable_no_storage`（去占用基表）与 `storage_entry_dirs` 按拓扑对象缓存，调用处只做浅拷贝 + 补端点。
2. **`_persist` 每 tick 全量落库**（simulation.py:874）：`update_run` 把整份运行状态（任务含完整 plan + 不断增长的历史）dumps 写库后又 **SELECT 回读 + loads 解码一遍，返回值被 `_persist` 丢弃**（纯浪费，~31% 采样）。→ 修复：`update_run` 去掉回读解码（用内存对象构造返回值）；常规 tick 落库降频为每 10 tick 一次（`_step_runtime` 内 tick % 10），结束/控制操作的 `_persist` 调用点保持即时。
3. shuttle 侧（上轮已修）的查找重建与路径记忆化继续生效。

另：用户编辑拓扑后**配置戳再次失配**（合同 409："expects 8eae0faf…, current 1347c70d…"）。按约定验证两台电梯在新拓扑上全部合格（footprint=True、min_degree=3）后把 `shuttle-v2.json` 更新为 `2.0.0:1347c70dbfcd1110`（config_revision → `shuttle-4l-lift-slotlifts-v2`），并把测试夹具 `topology_666.json` 重新同步为 DB 当前载荷、更新 revision 断言。

3. **取放链路**：`pickup_from_shuttle` 从货道库存移除被取箱（按 cellId+layer+depth）；倒库任务交付写入目标货道（`_complete_shuttle_relocate`，不走上带/拣货链路，交付层随目标货道）。

  - 单臂逐箱串行；后续车辆在地面线上自然排队（占格/绕行机制复用）。
  - 兜底：等待中车辆故障/取消 → 机械臂复位。
- 遥测：`arm_handoff` 事件（pick/place/placed 三阶段）进 WebSocket 白名单。
